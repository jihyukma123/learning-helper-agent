# Assumption Validation — Onboarding Tracker v0.1

Date: 2026-04-26
Context: ChatGPT Enterprise 고객-Reseller 공유 onboarding tracker (제품 방향 검토)

---

## Product 가설 (요약)

처음 framing했던 *"고객 안내용/문의용/관리용 플랫폼"* 에서, 더 구체적인 형태로 옮겨감:

> **표준화된 onboarding 체크리스트를 만들고, 고객은 그 순서대로 따라가게 하고, Reseller 팀은 각 고객의 진행 상황을 한 대시보드에서 보는 형태.**
> — 같은 데이터, 두 개의 view (고객용 / 내부용).

이 형태가 4개 pain (반복 안내 / 반복 confusion / 팀 협업 가시성 / 고객 상황 모름)을 모두 부분적으로 해결한다는 가설.

---

## 가정 1 — 표준화 가능성: "거의 모든 고객의 초기 프로세스가 거의 동일하다"

**검증 결과**: 부분 참 — *2단계 구조*로 분리됨.

### 1-A. 극초기 단계 (계정 발급 ~ 확인)
- 모든 고객 **완전 동일**
- 다르게 할 부분이 절대 없음
- → **강제 (force)** 가 가능하고, 강제되어야 함

### 1-B. 초기 설정 단계
- 일부는 공통, 일부는 고객별 변동 가능
- 변동 요인: SSO 연동 여부, IdP 종류 (SCIM 지원 여부), 보안 정책 등
- → **강제할 부분과 선택지 줄 부분을 명시적으로 구분**해야 함

### 의미
- 단순한 단일 linear 체크리스트로는 부족
- *공통 prefix + 조건부 분기* 구조가 필요
- v0.1 설계 시점에서 풀어야 할 핵심 문제: **"고객별 다를 수 있는 부분을 어떻게 customize해서 본인에게 필요한 내용만 표시할지"**

---

## 가정 2 — 고객 수용성: "고객이 '닥치고 따라해' 형식을 받아들일 거다"

**검증 결과**: 참.

- 본인 관찰: 고객들은 자유보다 명확한 가이드를 *더 선호*함
- 가이드 표준화하려는 단계들은 고객이 자율성을 발휘할 영역이 아님 (보안/권한 설정 같은 영역)
- 고객이 자기 상상대로 다른 순서로 시작할 가능성 자체를 제거하는 게 가치

### UX 보정 (마인드셋 기록)
- 내부 의도 = "닥치고 따라해 / drift 차단"
- 외부 표현 = "처음이세요? 같이 차근차근 가보시죠" (친화적 안내 정서)
- 강제처럼 *안 보이는데 사실은 고도로 강제*되는 onboarding UX (Stripe/Linear/Notion 정서)

---

## 가정 3 — 자동 verify 가능성: "체크리스트 체크 = 실제 작업 완료를 보장"

**검증 결과**: 거짓 — 자동 verify는 현재 불가능.

- OpenAI Admin API는 onboarding 단계 자동 verify 기능을 제공하지 않음 (2026-04-26 기준)
- → 모든 단계는 **고객의 자가 보고(self-check)** 에 의존

### 가용한 시그널
- 고객이 단계를 체크했을 때, **체크 시점 timestamp** 기록
- 이걸로 진행 흐름/속도/정체 지점은 어느 정도 추정 가능
- 단, "체크했다 ≠ 실제로 했다" 는 한계는 디자인 단계에서 명시적으로 인정해야 함

### 향후 모니터링 포인트
- OpenAI Admin/Usage API가 추후 step-level verify를 지원하면 가장 큰 업그레이드 포인트
- 정기적으로 OpenAI 업데이트 노트 체크 필요

---

## 결론 — v0.1 설계에 미치는 영향

1. **체크리스트는 단순 linear가 아니라 "공통 prefix + 조건부 분기" 구조**로 가야 함
2. **고객별 customize 로직** (SSO/IdP/SCIM 변동 케이스) — v0.1에서 풀어야 할 핵심 설계 문제
3. **모든 진행 상태는 자가 보고 기반** — 단계별 timestamp 기록이 데이터 모델의 핵심
4. **UX 정서 = 친화적 가이드**, 내부 의도 = drift 차단 — 두 층을 분리해서 설계
